# SuperSLM 1.19.0

**Unreleased.** This is a draft. Nothing below is certified yet, and the version numbers in the tree are unchanged.

SuperSLM 1.19.0 lets a schema contain JSON arrays, and states what the engine's `-2` means at the end of a
schema-bound reply, so a complete document ends cleanly instead of looking like a fault.

No ABI, struct layout, status or save format (`SSB5`, `SSB6`, `SLM5`, `SLM6`, `SPX1`) changes. An artifact without an
array schema needs no reconversion.

## What's new

### JSON arrays in schemas

- **The converter compiles arrays.** A `"type": "array"` node with one `items` schema becomes a repeating item: `[`,
  the `minItems` required items separated by commas, then `]` or another item. `minItems: 0` allows `[]`. A leading,
  trailing or doubled comma is never allowed, and arrays can nest.
- **What it refuses, by name.** `maxItems`, and any schema with a state the model could reach but never finish a
  document from.
- **Limits.** An array schema is held to seven limits, each refused with its own message: at most 8 `minItems` per
  array, nesting depth 8, 4,096 NFA states, 4,096 token-DFA states, 8,388,608 token transitions, 128 MiB of mask data
  and 512 MiB of compiler memory. A schema without an array is not held to them, and compiles to exactly the bytes it
  did before.
- **Attaching a schema to a finished model.** `tools/sslm_attach_schema.py` compiles your named schemas against the
  model's exact tokenizer checkpoint and appends them to a copy of the `.sslm`, leaving every other section unchanged.
  It verifies the model before and after, and writes nothing if anything is wrong: a damaged base, a base that already
  has schemas or has no tokenizer, a checkpoint that does not match, or a schema the converter refuses.
- **The verifier checks schemas.** `sslm_verify` now refuses a schema section the runtime would refuse. Before, an
  attach could report success on a model that would not load.
- **Proof on a real model, on the 1.19 engine.** The full array proof passed again on a Radeon RX 7900 XT, with the
  0.5B model and a schema with nested arrays ([tests/array-s2/RESULTS.md](../../tests/array-s2/RESULTS.md)): all 81
  steps. Every reply on all 10 prompts was valid and the same on CPU and GPU, token for token, and the same as before
  the 1.18 merge. Saving and restoring mid-array worked at all 54 points in generated replies and all 21 points in
  fixed documents, on both. GPU exact skip-ahead and GPU multi-row reading each gave the plain GPU reply on all 10
  prompts, at about 40 ms per token against 232 for plain GPU decode at the default setting.
- **Known issue (since 1.17.0): with a schema bound, keeping the output head on the GPU saves no time.** Since
  1.17.0, a schema-bound reply on a model whose head is tied to its embedding scores only the legal tokens, on the
  host, whatever the head setting. Inside a string almost every token is legal, so that costs about as much as the
  full host head: one-slice GPU decode took 26.8-28.5 ms per token with the head on the device or the host, against
  18.0 ms with the device head on a 1.16 base. The replies are unchanged.

### A clean stop at the end of a schema

When a schema-bound reply reaches a point where no token may come next, the engine returns `-2` at `SSLM_OK`. That
happens in two cases, and 1.19.0 tells you which:

| Accepting bit, read right after the `-2` | Meaning | What to do |
|---|---|---|
| 1 | **Clean stop.** The document is complete. | Stop decoding. The output is final. |
| 0 | **Dead end.** The reply cannot be completed. | Treat it as an error. |

- **On the CPU**, read `sslm_stats().schema_accepting`, or the `out_accepting` of `sslm_seq_forced_tokens`.
- **On the GPU**, call `SslmGpuSeqSchemaAcceptingForG5Bridge`, or read the `out_accepting` of
  `sslm_gpu_seq_forced_tokens`.
- Nothing else changes. The sequence keeps its state, so asking again gives the same `-2`, and the sequence can be
  saved, restored, reset or given a new adapter.
- A GPU exact skip-ahead whose draft runs through the schema's last token ends as a clean stop. Draft tokens past the last
  token are not admitted.

See [docs/api.md](../api.md) for the full contract.

### Qwen3 converter fixes

- **Qwen3-0.6B's checkpoint converts.** Its config ties the embedding and the output head, and its checkpoint
  also stores a copy of the head as `lm_head.weight`. When that copy has the same dtype, shape and stored bytes as
  the embedding, the converter now ignores it, and the result is exactly what the checkpoint gives without it. A
  copy that differs in any way is refused with `TiedLmHeadMismatch`, which names both tensors and what differs.
  Sharded checkpoints take the same rule, and so does `tools/sslm_convert_adapter.py --fallback=merge`, which before
  replaced a differing head with the embedding without a word. Models whose head is not tied are unchanged.
- **Relative tool paths in the conversion flow.** `--capture` and `--verifier` now resolve against the directory
  you run the command from, so `./t2700_fused_k_capture` runs that file and never a same-named program on `PATH`.
  A bare name runs the file in that directory if it is there, and is otherwise looked up on `PATH`.
- **Qwen3-0.6B needs `--channel-scale-headroom 1.25`**, as Qwen3-Embedding-0.6B does. At the default it clipped
  about 27.8 per million in pass C and was refused. See [docs/quickstart.md](../quickstart.md).
