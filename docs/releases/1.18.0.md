# SuperSLM 1.18.0

Released @RELEASE_DATE@.

SuperSLM 1.18.0 lets the GPU run several tokens through the model in one pass ("multi-row"), removes canonical
jump-forward, and adds an opt-in setting that threads multi-token passes on the CPU.

The GPU uses multi-row passes for two things:

- **Reading prompts**, in fewer frames.
- **Exact skip-ahead**: proposing several tokens of a schema-bound reply at once and keeping the ones the model would
  have chosen anyway.

The output is unchanged. Every token, and every byte of a save, is the same as the plain one-token-at-a-time GPU
path's. What changes is how many frames it takes. No save format (`SLM5`, `SLM6`, `SPX1`) changes, and no model
artifact needs reconversion. `SPX1` prefix blobs are bound to the engine version, so rebuild prefix caches made by
1.17.0 (1.18.0 refuses them with `SSLM_RESTORE_PRODUCER_MISMATCH`). SuperSLMUnreal 1.4.0 vendors this release.

## What's new

### Multi-row GPU passes

- **Prompt reading.** The GPU prompt bridge reads a prompt in passes of up to 8 tokens instead of one token at a
  time, still within the per-frame GPU budget you set (`dispatch_budget`).
  - On the certification card with the 0.5B model, a prompt that took 123 frames to become ready one row at a time
    took 47 frames in a one-call setup at no frame cap. In a composed setup it went from 738 frames to 372.
  - These are frame counts. Wall time depends on your frame rate.
  - Setting `SSLM_GPU_MULTIROW_PROMPT=0` before `sslm_gpu_context_create` keeps 1.17.0's one-row path. Results are
    byte-identical either way.
- **Exact skip-ahead on the GPU.** `sslm_gpu_seq_jump_forward` now runs exact mode: the pending token and the draft
  (the caller's, or the forced chain) go through the layers in passes of up to 8 rows, and the call keeps every
  proposed token up to the first one the model would not have produced. The reply is identical to skip-ahead off,
  token for token.
- **The speedup depends on your setup and budget, is sometimes none, and can be a loss.** All figures below are for the 0.5B model
  on the AMD Radeon RX 7900 XT: four agents, 84 tokens in total, exact against off on the same setup.

  | Setup, GPU budget per frame | Off | Exact |
  |---|---|---|
  | One call, no cap | 84 tokens in 1.73 s, 48.4 tok/s | 84 tokens in 1.35 s, 62.2 tok/s |
  | One call, 2 ms | 84 tokens in 4.22 s, 19.9 tok/s | 84 tokens in 2.18 s, 38.5 tok/s |
  | One call, 4 ms | 84 tokens in 2.84 s, 29.6 tok/s | 84 tokens in 2.12 s, 39.6 tok/s |
  | Mixed, no cap | 84 tokens in 3.51 s, 24.0 tok/s | 84 tokens in 4.17 s, 20.1 tok/s |
  | Mixed, 4 ms | 84 tokens in 4.01 s, 21.0 tok/s | 84 tokens in 3.59 s, 23.4 tok/s |
  | Composed, 4 ms and up | about 16–18 tok/s | the same: exact runs as off in this setup |

  With the 1.5B model, only off was measured: 16 tokens in 3.1 to 5.2 s, depending on setup and budget.

  These are one card, one model and one workload. Your figures will differ. Measure on your own target hardware.
  Exact never changes the reply, so it is safe to turn on; measure whether it is faster on your setup.

- **The verbs.** `sslm_gpu_seq_embed_rows` opens a row chunk of up to `SSLM_GPU_MAX_ROWS` (8) tokens
  (`SslmGpuRowsSpec`, kind `SSLM_GPU_ROWS_PROMPT` or `SSLM_GPU_ROWS_EXACT_DRAFT`). The decode step, and a batch
  member, then runs the chunk's layers as one widened dispatch per site, and the close commits the rows.
  `sslm_gpu_seq_rows_abandon` puts the sequence back as it was before the chunk. `sslm_gpu_seq_rows_open`,
  `sslm_gpu_seq_last_rows_committed` and `sslm_gpu_seq_rows_produced` read the chunk's state.
- **One new GPU status.** A save with a chunk open returns `SSLM_GPU_ROWS_CHUNK_OPEN` (`SslmGpuStatus` 33) with
  nothing written. It is GPU-only: no CPU call can return it, so the CPU's status list does not carry it.
  `sslm_gpu_seq_embed_rows` with no headroom before the context cap returns 1.17.0's `SSLM_GPU_CONTEXT_CAP_EXCEEDED`.

See [docs/api.md](../api.md#multi-row-prompt-reading-1180) for the full contract.

### CPU: threaded multi-token passes (opt-in)

A new parallel-for bit, `SSLM_PARALLEL_FOR_PREFILL` (bit 0 of `sslm_parallel_for.reserved`), spreads passes of two
or more tokens across your thread pool: prompt reading, prefix building and skip-ahead checks.

- It is off unless you set it.
- Tokens and saved state are byte-identical with it on or off.
- Skip-ahead still checks short drafts (2–7 tokens) one row at a time. That stops at the first rejected token,
  which measured faster than the threaded pass: 0.98× against 0.86× of plain decoding, on a 16-core CPU with the
  default draft.

## Removed: canonical jump-forward

**Canonical is removed on the CPU and the GPU. Mode 0 is now `SSLM_JUMP_DEFAULT`, which selects exact mode, as do
NULL options.**

- Canonical wrote forced text with the tokenizer's own spelling instead of the model's. That changed answers, not
  only tokens (1.17.0 deprecated it).
- Code that zero-initialised the options, or passed NULL, keeps compiling and now gets exact mode. A caller's draft
  still takes `SSLM_JUMP_EXACT`.
- Saves made by 1.15.0–1.17.0 after a canonical jump still restore.

## Changes you might notice

- **Several agents advancing together still cost one GPU submission each.** When several agents each have a
  multi-row pass in flight in the same frame, each gets its own GPU submission, not one shared submission. Results
  are unaffected. The cost is a little more per-frame overhead in busy composed scenes.
- **Which AMD card is certified.** The AMD card certified for multi-row is the Radeon RX 7900 XT (20 GB).

## In SuperSLMUnreal 1.4.0

The plugin that vendors this release adds:

- **Load-time GPU cost calibration.** When a model's GPU path is configured, the plugin times the model on the
  player's card and sizes each frame's work from that, unless your game sets the cost itself (your setting still
  wins). The fixed 6.2 ms default under-priced the 1.5B model on the RX 7900 XT, which measured 10.9 ms. The first
  generation after a model loads waits for this short measurement.
- **Later tokens are priced higher.** The timing is taken at two context positions, and each slice is priced at its
  position with a small margin, so the price keeps up as a reply grows.
- **One hitch during load no longer skews the price.** A timing far slower than the others is discarded and re-taken.
- **GPU exact proposes the model's own spelling.** The plugin's GPU exact skip-ahead proposes the same learned draft
  as CPU exact, instead of the tokenizer's spelling of forced text, which the model often doesn't use. Replies were
  never affected, only speed.
- **The Canonical setting is gone.** An old project's saved setting falls back to the default, Off.

## Certified hardware

- **AMD Radeon RX 7900 XT**, the certified card for multi-row GPU in 1.18.0. Every build and every automated suite
  passed, and 26 of 28 frame-timing lines held the budget at the 99th percentile (two misses: see Known issues).
- **NVIDIA RTX 5060: kernel equality passed.** On driver 32.0.16.2101 the multi-row kernels gave the same tokens as
  the reference on every check, so multi-row is correct on RTX 50-series. Its timing was not certified.
- GPU frame timing is measured and reported, not certified to the frame.

## Known issues

- **On a card that slows under sustained load, a 2 ms budget can run up to about 20% over for a stretch.** In
  certification, two of the 2 ms lines ran a stretch of consecutive frames at 2.0–2.6 ms while the card ran slow; their
  99th-percentile frames were 2.05 ms and 2.38 ms, and they delivered 12 to 12.5 tok/s against 18 to 21 normally. Larger
  budgets were not affected.
- **A schema dead end is still a fault until 1.19.0.** If a schema-bound generation reaches a state with no legal
  continuation, the sequence faults rather than ending cleanly. Make sure your schemas can always close.
- Array schemas are not convertible before 1.19.0 (unchanged from 1.17.0).
