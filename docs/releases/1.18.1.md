# SuperSLM 1.18.1

Released 2026-10-31.

SuperSLM 1.18.1 is a fix release for the GPU backend. A process that had used the GPU could crash as it exited
normally, when the library was built into a DLL: the Unreal Engine editor and its commandlets, with the SuperSLM-Unreal
plugin, exited with `0xC0000409` after any GPU work. The library no longer releases any D3D12 object from a static
destructor. No token, save format, status, verb or shader changes from 1.18.0, and no model artifact needs
reconversion. `SPX1` prefix blobs are bound to the engine version, so rebuild prefix caches made by 1.18.0.

## What changed

- **The process's GPU device and the GPU pipeline caches are never destroyed.** The device every GPU call submits
  on, the two pipeline caches, the shared root signature and the descriptor-table probe's pipeline were static
  objects, destroyed among the static destructors at exit. In a DLL those run at the DLL's process detach, after the
  D3D12 runtime has torn down its own state, so the device's last release failed fast inside
  `D3D12NotifyDeviceDeletion` (`0xC0000409`, `FAST_FAIL_FATAL_APP_EXIT`). They now live until the process ends,
  and the operating system reclaims them then. A context's own device (`sslm_gpu_context_destroy`) is released as
  before.
- **A source lint keeps it that way.** `tests/ci/check_gpu_no_exit_destructors.py` reports any static-storage
  object under `src/` or `include/` that holds a D3D12 object by value. It runs in the tests workflow, and its red
  suite in `pytest tests/ci/`. At 1.18.0 it reports the six objects above.

Who was affected: a host that loads the library from a DLL and exits through the C runtime (returning from `main`,
or `exit`) after using the GPU. An executable that links the library statically runs its static destructors before
the D3D12 runtime unloads, and did not crash; neither did a host that ends with `TerminateProcess`, which runs no
destructors.

## Compatibility and required action

- No ABI, save format, status, verb or shader change. Tokens and `SLM5` and `SLM6` saves are byte-identical to
  1.18.0's.
- **Rebuild prefix caches made by 1.18.0.** An `SPX1` blob records the engine version that wrote it, patch included,
  and 1.18.1 refuses a 1.18.0 blob with `SSLM_RESTORE_PRODUCER_MISMATCH`.
- A process that creates and destroys many GPU contexts is unaffected: a context's device is released at
  `sslm_gpu_context_destroy`, as before. The objects kept to exit are the one process device and the pipelines
  built on it.

## Verification

Windows x64, MSVC, on an AMD Radeon RX 7900 XT:

- **The exit.** In the SuperSLM-Unreal 1.4 editor build, the prefix-set commandlet and an editor session ended through
  the normal exit path after GPU work exited `0xC0000409` on 1.18.0, every time. On 1.18.1 the commandlet exited 0 on
  both of two runs, and both GPU sessions exited 0.
- **The plugin's GPU suites.** The prefix cache, paging, multi-row, schema jump-forward and frame-budget suites, with
  the library at this fix: 247 of 248 cells passed. The one red is a timing cell on the 1.5B model, outside certification
  on this card and red before this fix. GPU timing is measured, not a gate.
- **The version.** The prefix cache suites again on 1.18.1 proper, with prefix sets rebuilt: 151 of 153 cells passed.
  One red needs a recorded asset that is not on this machine. The other is a plugin test that assumes 16 requests
  land in one pass; it passed six of six repeats, and the behaviour it caught is correct.
- **The library's own tests.** CTest on this machine: 30 of 41 passed, 29 on 1.18.0. The 11 that did not are the
  same on 1.18.0: they need model fixtures or a layout this machine's build does not have.
- **The lint.** 6 findings on 1.18.0, 0 on 1.18.1, and its 8 fixture cells pass.
