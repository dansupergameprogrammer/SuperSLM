# SuperSLM 1.14.0: test results

This page summarizes the testing behind 1.14.0's CPU frozen-prefix save and restore (`sslm_prefix_save`,
`sslm_prefix_restore`, the `SPX1` blob). It is written for developers deciding whether to use the feature. The
release note, [`1.14.0.md`](1.14.0.md), describes the API. The raw logs and per-run records are kept on the
development branch, not here.

Test cells are named the way the test sources name them, for example `9.1/E2`. Each source file lists its cells in its
header.

## In short

- A restored prefix behaves like the prefill-built one. Its adopters produce the same tokens, and saving it again
  produces the same bytes. This was checked on synthetic models, on the real 0.5B and 1.5B artifacts, across three
  compilers, and under ThreadSanitizer.
- Restoring is much faster than prefilling the same prompt again. The ratios below are measured with **one thread**
  and with the blob **already in memory**. A multi-threaded prefill, or a restore that first reads the blob from disk,
  narrows the gap. Measure your own case before you budget on these numbers.
- A blob is tied to the engine version that wrote it. Any other version refuses it with
  `SSLM_RESTORE_PRODUCER_MISMATCH`, so you need to regenerate saved prefixes when you upgrade.

## Restore against prefill (real 0.5B model)

The machine was an AMD Ryzen 9 3950X on Windows 10, with an MSVC 19.34 Release build. Each run used one thread and
page size B = 128, with eight paired runs per prompt. The restore time includes verifying the blob's SHA-256 digest.

| Prompt (tokens) | Blob size | Prefill | Restore | Restore is faster by (95% range) |
|---|---|---|---|---|
| 159 | 0.93 MiB | 2,025.8 ms | 0.558 ms | 3,536–3,732× |
| 258 | 1.51 MiB | 3,323.6 ms | 0.884 ms | 3,718–3,799× |
| 380 | 2.23 MiB | 4,954.8 ms | 1.286 ms | 3,828–3,879× |
| 501 | 2.94 MiB | 6,692.0 ms | 1.707 ms | 3,876–3,967× |
| 751 | 4.40 MiB | 10,433.9 ms | 2.585 ms | 3,880–4,207× |
| 1,000 | 5.86 MiB | 14,497.5 ms | 3.430 ms | 4,092–4,372× |
| 1,208 | 7.08 MiB | 18,036.5 ms | 4.167 ms | 4,298–4,358× |
| 1,506 | 8.83 MiB | 23,567.9 ms | 5.519 ms | 4,204–4,339× |
| 1,801 | 10.55 MiB | 29,478.0 ms | 6.915 ms | 4,217–4,311× |
| 2,000 | 11.72 MiB | 33,600.6 ms | 7.702 ms | 4,330–4,396× |

- Prefill cost 12.7–16.8 ms per token on one thread. Restore cost about 0.6 ms per MiB of blob.
- Before these runs, the timing instrument had to tell a broken restore from a working one. With restore replaced by
  a re-prefill it measured 1.0–1.1×, and the real build measured above 3,600×.
- No other process used more than 13 CPU-seconds during any measured slice.

## The largest case (1.5B model, full 32,768-token context)

This is a prefix filling the whole context on the 1.5B geometry (28 layers, 2 KV heads, head size 128, page size 64).
Its blob is 469,763,768 bytes (448 MiB).

| Step | Machine | Result |
|---|---|---|
| Prefill and save | Intel Core i5-14400F, Windows 11, MSVC 19.34, one thread | 3,815.9 s (63.6 min), about 116 ms per token |
| Restore | AMD Ryzen 9 3950X, Windows 10, MSVC 19.34 | **315.6 ms** (about 0.70 ms per MiB, 1,420 MiB/s) |

- The restored prefix re-saved to the same bytes, and the cell (`10.3/E4:worst`) is green with 38 checks.
- The two times come from **different machines**, so the ratio between them (about 12,000×) is not a like-for-like
  speed-up. The restore time on its own is the figure to plan with. Note that a 448 MiB blob also costs whatever
  your storage takes to read it.

## The same bytes from every compiler

- **Blob bytes.** The same 1,000-token prefix (`4.3/E4`) produced byte-identical `SPX1` blobs on all three builds:
  MSVC 19.34 on Windows, GCC 13.3 on Linux and Clang 18.1 on Linux.
- **Cross-build restore.** A blob written by the GCC build was restored by the MSVC Release build (`9.1/E2`), and
  saving the restored prefix again reproduced the MSVC build's own blob exactly. The cell was **green, 32 checks**.
  Before the restore, the cell checked the GCC blob against a recorded build of its producer: compiler, runner and
  logs, all hashed.

## ThreadSanitizer (Linux, GCC 13)

Every run reported **0 ThreadSanitizer warnings**:
- the save/restore suite, including the concurrent restore, adopt and page-sharing cells;
- the full engine unit suite.

In those two suites, the red cells were the same as in a run without ThreadSanitizer, and each one needs an input the
run did not have, such as a model file. Also green with 0 warnings:
- 22 longer cells. The two 32k-context cells, `4.7/E2:pkv_32k` (2,566 checks) and `9.8/E2:pkv_32k` (1,987), each
  ran about 3.1 hours.

The independent adversarial review also ran a six-thread attack, with concurrent restores (with and without a
parent hint), adopts, saves and children begun from one parent. Its tokens and blobs matched the serial run, and
ThreadSanitizer found nothing in the library.

## Reference streams for the restore tests

The cells that compare a restored prefix's output against pinned prefill output use reference streams that were
regenerated on the release's base commit. Each pair of runs was byte-identical, and every reference is bound to a
commissioned discrimination record. The test loader refuses any reference outside that licence.

- **Real 0.5B, flat and nested prompts (100 adopters):** `10.1/E4`, 4,184 checks, and `10.2/E4`, 4,378 checks, both
  green. The page draw matched for every nested prompt.
- **Synthetic, one flat and one nested prompt:** `6.2/E2:reference`, **316 checks**, and `6.3/E3:reference`, **325
  checks**, both green. Each graded 2 of 2 adopters.
- **Negative checks.** A reference with one token edited and re-licensed turned the cells red. So did a licence over
  the wrong record set.

## Reviews

- **Adversarial review of the save, restore and nested-sharing contract: CLEAR.** The review covered 11 lines of
  attack:
  - fidelity at boundary lengths on three geometries;
  - nested restores with and without the parent;
  - wrong-parent hints;
  - about 600 hostile but well-formed blobs under AddressSanitizer and UndefinedBehaviorSanitizer;
  - one-bit flips and truncations, all refused;
  - identity mismatches, each refused with its documented status;
  - schema-bound prefixes;
  - concurrency;
  - the save buffer edges;
  - the 32k cap.

  It found no input that breaks a documented promise.
- **Final code review of the release changes: SHIP.** It reproduced the 9.5 pins byte for byte, and it confirmed that
  the pinned test inputs survive a Windows CRLF checkout unchanged. It found only record-keeping issues, which are
  fixed.
