Decode threading D1 -- cells 6.3 and 9.1 against the v1.9.0 library (local evidence, not a suite cell)

The suite's 6.3 compares bit-1-on against chunk-1 no-hook in the same library; the plan's "v1.9.0's pin" is
the same generator's artifact run on v1.9.0. 9.1 needs a v1.9.0 build. Both are run here with v190_blob_probe.cpp,
built twice with GCC 13 -std=c++20:
  - against the v1.9.0 tag's libsuperslm.a (d870d27, Release): no hook (v1.9.0 has no bit 1);
  - against D1's superslm_test_injection library: bit 1 on, max_tasks 4, the reference-order-reversed inline
    hook, minimum-work seam 8 KiB so every M = 1 site threads.
save: 64 one-token prefills of a 64-token prompt, then sslm_seq_save. cont: sslm_seq_restore, save again (the
round trip), 8 greedy decode tokens, save.

== Re-run at the review-fix head (code review P4, 2026-09-30)
The review found the F-QK above differs from the one its Windows host generates (31dd0c5b...). The cause is numpy's
CPU-dispatched float64 exp reaching F-QK's QKC1 table (fixture-premise.txt, "Host dependence of F-QK"); the engine is not
involved. Both runs above were repeated with fixtures freshly generated at this head: the v1.9.0 tag's libsuperslm.a
(d870d27) against the head's superslm_test_injection (GCC 13), probe unchanged. The extra F-QK variant is the one this
host generates with numpy's AVX-512 dispatch disabled, the build a non-AVX-512 host's numpy takes.
